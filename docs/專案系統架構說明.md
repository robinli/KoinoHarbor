# Koino Harbor 專案系統架構說明

## 概要

Koino Harbor 是企業內部溝通平台的 POC。網站採用 Google Cloud 與 Firebase 的全代管 Serverless 架構：Cloud Run 執行 Node.js 網站與 API，Firebase 提供帳號驗證、文件型資料庫與附件儲存。

```text
使用者瀏覽器
    │ HTTPS
    ▼
Google Cloud Run
    │ Node.js 網站、靜態前端、REST API、Session 與權限檢查
    ├──────────────► Firebase Authentication
    │                 Email/Password 登入、ID Token、使用者帳號
    ├──────────────► Cloud Firestore
    │                 使用者、Space、討論串、回覆、書籤、附件中繼資料
    └──────────────► Cloud Storage for Firebase
                      附件實體檔案
```

## 資料流與安全性

1. 使用者透過瀏覽器以 HTTPS 連至 Cloud Run。
2. 使用者使用 Firebase Authentication 的 Email/Password 登入；Cloud Run 驗證 Firebase ID Token，並建立 HttpOnly Session Cookie。
3. Cloud Run 以 Firebase Admin SDK 存取 Firestore 與 Cloud Storage，所有業務權限檢查均在後端執行。
4. Firestore 儲存討論內容與附件 metadata；附件二進位內容存放在 Cloud Storage。
5. `Admin`、`Member`、`Guest` 為固定單一群組；頂層與 restricted 子工作區以 `allowedRoles` 控制加入資格，inherited 子工作區則純繼承父層成員。軟刪除的工作區不提供內容存取；Admin 的全域管理權不會自動授予內容權限。

## 主要資料

- `users`：使用者帳號資料、角色與啟用狀態。
- `spaces` 與 `spaces/{spaceId}/members`：部門／專案空間的允許群組與直接加入關係。
- `threads` 與 `threads/{threadId}/replies`：討論串與回覆。
- `threadStatuses`：討論串狀態。
- `users/{userId}/bookmarks`：使用者書籤。
- `attachments`：附件 metadata；檔案本體位於 Cloud Storage 的 `spaces/{spaceId}/threads/{threadId}/` 路徑。

## 成本控制原則

- Cloud Run 使用 request-based billing，最小實例維持為 0，避免閒置計費。
- Cloud Run、Firestore 與 Storage 應使用相同或相近區域，降低延遲與跨區傳輸成本。
- 附件下載流量與長期保留容量是最主要的變動成本；應設定 Billing Budget、用量告警與附件保留／清理政策。
