# 企業內部溝通平台技術選型報告

## 1. 專案背景

本專案目標為建置一套企業內部溝通與討論平台，功能概念以舊版 Microsoft Yammer 類型的企業社群為基礎，但聚焦於小型企業實際需要的討論、分類與追蹤功能，不以即時聊天或大型社群功能為主要方向。

目前預計使用規模為 **單一公司、20 人以下**，採 Web 網站形式提供服務，需可長期使用並具備帳號登入、資料持久化、附件管理及權限隔離功能。

---

# 2. 需求摘要

## 2.1 使用情境

- 單一公司使用
- 使用人數：20 人以下
- 主要使用者為公司內部員工
- 可邀請外部使用者
- 外部使用者只能存取被邀請加入的特定專案討論區
- 系統以 Web 網站形式提供
- 需長期常駐使用
- 預期流量低

## 2.2 核心功能

### 討論區

系統需可建立不同類型的討論空間，例如：

- 部門討論區
- 專案討論區

建議系統內統一抽象為 `Space`，再利用類型欄位區分 Department 與 Project，避免開發兩套不同的討論區架構。

例如：

```text
Spaces
├─ 財務部
├─ 業務部
├─ 行銷部
├─ ERP 導入專案
└─ 客戶 A 專案
```

### 討論串

每個 Space 可以建立多個討論串 Thread。

討論串需支援：

- 標題
- 內容
- 作者
- 回覆
- 附件
- 圖片
- 個人書籤
- 置頂
- 狀態
- 封存
- 全文搜尋

### 狀態管理

討論串狀態不得寫死於程式中。

系統管理員可以自行建立及管理狀態，例如：

```text
未處理
處理中
等待回覆
已完成
取消
```

建議第一版採用：

**全公司共用狀態設定**

管理員可進行：

- 新增
- 修改名稱
- 排序
- 停用

未來如有需求，再擴充為每個 Space 可設定不同狀態。

# 4. Google Cloud Run 選型理由

## 4.1 適合低流量企業內部系統

本系統只有約 20 名使用者，不屬於高流量網站。

Cloud Run 預設支援 request-based billing，在服務實例處理請求、啟動或關閉時才產生主要運算費用；Cloud Run 官方目前亦提供每月免費運算與請求額度，包括 request-based billing 下每月 200 萬 requests 的免費額度。

因此非常適合以下模式：

```text
上班時間
   │
   ├─ 員工偶爾登入
   ├─ 閱讀討論
   ├─ 新增 / 回覆
   └─ 上傳附件

下班 / 無使用者
   ↓
Cloud Run Scale to Zero
```

建議：

```text
Minimum instances = 0
Maximum instances = 2～3
CPU = 1 vCPU
Memory = 512MB～1GB
```

不建議此階段保留固定常駐 Instance，因為使用量太低，沒有必要支付閒置資源費用。

# 5. Firebase Authentication

使用者登入方式採：

**Email + Password**

Firebase Authentication 可直接負責：

- 帳號建立
- Email / Password 登入
- 密碼重設
- Session / Token 驗證
- 停用帳號

本專案使用者只有 20 人左右，遠低於 Firebase Authentication 一般使用規模；Firebase Authentication 亦提供免費使用層級，若未來升級 Identity Platform，其計費模型則有所不同。

因此不建議自行開發密碼管理與登入系統。

# 6. 使用者角色與權限

建議採三層角色：

| 角色 | 用途 |
|---|---|
| Admin | 系統管理員 |
| Member | 公司內部使用者 |
| Guest | 外部使用者 |

## Admin

可以：

- 建立 Space
- 建立 Department / Project
- 管理使用者
- 邀請 Guest
- 管理狀態
- 管理置頂
- 封存討論串
- 管理成員

## Member

可以：

- 查看有權限的討論區
- 建立討論串
- 回覆
- 上傳附件
- 加入個人書籤

## Guest

Guest 必須使用「Explicit Membership」模式。

也就是：

```text
Guest
  │
  ▼
Space Membership
  │
  ▼
只能看到指定 Project
```

例如：

```text
公司空間

├─ 公司公告
│   └─ Guest ❌
│
├─ 財務部
│   └─ Guest ❌
│
├─ 業務部
│   └─ Guest ❌
│
└─ 客戶 A 專案
    ├─ 員工 A
    ├─ 員工 B
    └─ vendor@example.com ✅
```

Guest 不應取得任何公司層級預設讀取權限。

這會是整個系統最重要的安全設計之一。

# 8. Firestore 選型理由

Cloud Firestore 是 Serverless Document Database，不需要自行管理資料庫主機、Patch、Replication 或 Capacity。Google 官方亦將其定位為可自動擴縮的 Fully Managed Serverless Database。

對本專案而言主要優點是：

1. 不需要管理 SQL Server
2. 不需要 PostgreSQL Server
3. 不需要 Database VM
4. 與 Firebase Auth 整合容易
5. 與 Firebase Storage 權限容易整合
6. 20 人資料規模非常小

Firestore 主要依文件讀取、寫入、刪除、索引、儲存與網路使用量計費。

因此在本案的低使用量下，很適合採 Pay-as-you-go 型態。

   │
   └──────► Firestore 儲存 Metadata

Firebase Storage 可整合 Firebase Authentication 建立檔案存取控制。

建議限制：

```text
單檔最大：20～50 MB
```

- JPG

- WebP

- Office 文件
- ZIP（視公司需求）

原因是影片會快速增加 Storage 及 Network Transfer 成本。

# 10. 全文搜尋方案

這是本專案唯一不能完全依賴 Firestore 原生能力的部分。

Firestore 適合：

```text
status == Processing
spaceId == ABC
authorId == User001
archived == false
```

但不適合直接當完整 Full-text Search Engine。

例如搜尋：

```text
ERP 報價錯誤
```

希望同時搜尋：

- Thread Title
- Thread Content
- Reply

這類需求未來較適合專門搜尋引擎。

## 第一版建議

**暫時不要加入 Elasticsearch / Algolia / Meilisearch。**

原因：

20 人以下的資料規模非常小。

第一版優先：

```text
簡單關鍵字搜尋
+
標題 / 內容索引策略
```

目的是保持架構簡單。

## 第二階段

當討論資料量明顯增加，再增加：

```text
Firestore
    │
    ▼
Search Sync
    │
    ▼
Meilisearch / Typesense / Algolia
```

如果未來選擇自行管理搜尋服務，本案較偏向：

**Meilisearch**

但目前不需要。

# 12. 成本估算

## 12.1 Cloud Run

Cloud Run request-based billing 目前包含免費額度，例如每月：

- 180,000 vCPU-seconds
- 360,000 GiB-seconds
- 2 million requests

實際免費額度的價值與地區定價相關。

20 人以下的內部網站，如果：

```text
min instances = 0
```

通常 Compute 使用量非常低。

### 預估

**US$0～3 / 月**

此數字為依本案低流量使用模式所做的工程預估，而非 Google 固定報價。

---

## 12.2 Firestore

Firestore 主要依：

- Document Reads
- Document Writes
- Deletes
- Index Reads
- Storage
- Network

計費。

假設：

```text
20 Users

每人每天：
100 Reads
10 Writes
```

約：

```text
每日
2,000 Reads
200 Writes

每月
60,000 Reads
6,000 Writes
```

這屬非常低的資料量。

Firestore 官方亦提供免費額度，超過才需啟用付費計費。

### 預估

**US$0～數美元 / 月**

---

## 12.3 Firebase Storage

Firebase 目前 Cloud Storage 類型及 Bucket 類型的免費額度與後續計費方式有所差異；新的 `*.firebasestorage.app` Bucket 目前可享一定的免費 Storage 與 Download 額度，超量後依 Google Cloud Storage 費率計算。

因此真正需要注意的是：

**附件容量，而不是文字討論資料。**

如果：

```text
20 人
+
主要為文件與少量圖片
+
不儲存大量影片
```

成本仍會非常低。

---

## 12.4 總成本預估

| 項目 | 預估月費 |
|---|---:|
| Cloud Run | US$0～3 |
| Firebase Auth | 約 US$0 |
| Firestore | US$0～數美元 |
| Firebase Storage | US$0～數美元 |
| 網域 | 另計 |
| **總計** | **約 US$0～5/月起** |

- 低頻率企業內部使用
- 無大量圖片
- 無影片
- Cloud Run Minimum Instances = 0

若附件資料量或流量上升，費用需重新估算。

# 13. 開發麻煩程度

## 整體評估

**低～中**

Cloud Run 比 Zeabur 多一些初始設定，包括：

- Google Cloud Project
- Billing
- IAM
- Service Account
- Artifact Registry / Build
- Environment Variables
- Deployment

所以單純比較「部署有多省事」：

```text
Zeabur
★★★★★

Cloud Run
★★★★☆
```

但本案同時使用：

```text
Firebase Auth
Firestore
Firebase Storage
```

Firebase 本身與 Google Cloud 屬於同一生態，因此長期維運反而可以集中：

```text
Google Cloud
├─ Cloud Run
├─ Firestore
├─ Firebase Auth
├─ Cloud Storage
├─ IAM
├─ Logging
└─ Billing
```

相較：

```text
Zeabur
+
Firebase / Google Cloud
```

會少一個外部平台。

因此對正式企業內部系統而言，Cloud Run 增加的初始麻煩是合理的。

# 14. 不建議方案

## Firebase Functions 作主要 Backend

不建議。

Functions 可處理：

- Trigger
- 排程
- 少量背景工作

但不建議把整套 Web Backend 拆成大量 Functions。

原因是：

- Functions 數量增加後管理較麻煩
- Local Debugging 較不直覺
- Deployment 分散
- 未來搜尋、附件處理與管理功能增加時更容易複雜化

因此：

```text
主要 Backend
→ Cloud Run

Event / Trigger
→ 未來需要時再考慮 Functions
```

---

## Apps Script

不建議。

雖然功能上可以完成部分需求，但是：

- UI 開發不方便
- Debug 麻煩
- 權限管理不適合這種架構
- 附件與複雜資料模型不自然

本專案不是 Apps Script 的適用場景。

---

## Colab / Gradio

淘汰。

不適合 24/7 企業內部正式 Web 系統。

---

## Replit

可作 Prototype。

但正式長期部署仍建議 Cloud Run。

# 15. 安全設計

本系統會有外部 Guest，因此安全設計比一般純內部工具更重要。

## 必須落實

### Authentication

所有受保護頁面必須要求 Firebase Authentication。

### Authorization

不能只判斷：

```text
已登入？
```

必須同時判斷：

```text
已登入
+
是否屬於該 Space
```

尤其 Guest。

### Storage Rules

附件不能使用永久 Public URL。

應依使用者及 Space Membership 控制存取。

### Server-side Authorization

重要權限不能只依靠前端 UI 隱藏。

Cloud Run Backend 必須重新驗證 Firebase Token 與使用者權限。

### HTTPS

Cloud Run 本身可透過 HTTPS 對外提供服務。

### Audit

建議保留：

- createdAt
- createdBy
- updatedAt
- updatedBy

關鍵管理行為未來可再增加 Audit Log。

# 20. 最終結論

## 🎯 最終選型

**Google Cloud Run + Node.js Web + Firebase Authentication + Cloud Firestore + Firebase Storage**

架構：

```text
                  ┌────────────────────┐
                  │      Browser       │
                  └─────────┬──────────┘
                            │
                          HTTPS
                            │
                            ▼
                  ┌────────────────────┐
                  │ Google Cloud Run   │
                  │                    │
                  │ Node.js Web App    │
                  └─────────┬──────────┘
                            │
           ┌────────────────┼────────────────┐
           │                │                │
           ▼                ▼                ▼
    Firebase Auth      Cloud Firestore   Firebase Storage
         │                  │                 │
      使用者登入        討論 / 權限          附件 / 圖片
```

本方案適合目前：

> **單一公司、20 人以下、企業內部使用、Web 形式、可邀請外部 Guest 的討論管理系統。**

Cloud Run 採：

> **Request-based Billing + Minimum Instances = 0**

可以讓低流量系統在閒置時盡量減少運算成本。Cloud Run 官方目前亦提供 request-based billing 免費額度，因此本案的運算成本有機會維持極低。

Firebase 則集中負責：

```text
Auth
+
Firestore
+
Storage
```

從而避免自行維護帳號系統、Database Server 與 File Server。

### 最終評語

**技術適配度：★★★★★**

**成本：★★★★★**

**正式環境適配：★★★★★**

**開發麻煩程度：低～中**

**未來擴充性：★★★★★**

綜合成本、功能、安全、維運與開發麻煩程度後，**Cloud Run + Firebase 為本專案目前最適合的技術選型。**
